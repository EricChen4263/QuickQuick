0. 摘要：五个必须先接受的判断

在给出方案前，有五个判断会直接改变方案形状。它们不是修辞，是本轮调研推翻或确认的事实。

判断一：Maccy 的功能面比「标杆」印象窄得多。 实测它的功能边界是：6 类 pasteboard 类型、200 条上限、4 种搜索模式、6 个设置页、0 个右键菜单、0 个多选、0 个粘贴栈、0 个导入导出、0 个多词 AND 搜索。它没有 OCR 之外的内容理解，没有翻译，存储不加密。

所以「全面看齐 Maccy」如果按字面理解，是一个比想象中小的目标。真正值得看齐的是它把一条窄路径打磨到极致的部分：交互模型、捕获完整性、规则系统、搜索手感、本地化工程。

判断二：粘贴栈不存在，不要为它立项。 调研初期我曾把它列为 Maccy 的核心能力（这也是社区常见误解）。全量枚举 76 个 Swift 文件后确认：Maccy 2.6.1 没有任何 Paste Stack / 队列 / 多选实现。它用两套机制覆盖「连续粘贴」需求：

  • 字母 pin：pin 字段存单个字母（b–y，排除 a/q/v/w/z），20 个键位持久化在库里，重启不变。按 b/c 即取该条粘贴。
  • 数字直达：前 10 条 unpinned 自动绑定 1–0。

体验上比粘贴栈少一步（不需要先组队列），但覆盖不了「临时挑 5 条按顺序贴进一个表单」。这是 QuickQuick 可以超越的地方，不是「看齐」项。

判断三：交互重构的技术路径已被同栈项目验证，风险从「成败未定」降为「适配工作量」。 Maccy 交互体验的根基是 NSPanel(.nonactivatingPanel)——点开面板不激活 Maccy。这一个决策消灭了整类 bug：不需要记录/恢复前台应用，不需要 NSApp.activate，粘贴必然落到正确目标，用户原应用的光标与选区完全不变。

初版方案把「Tauri webview 能否在非激活面板拿到键盘焦点」列为单点成败风险。这个判断过重了，已被实证推翻：

  • 存在成熟库 tauri-nspanel（crates.io 2.1.1，12,593 下载），定位即「subclassing Tauri's NSWindow to NSPanel」，机制是 object_setClass 把 NSWindow 改成动态生成的 panel 子类。
  • 存在同技术栈、同品类的成功先例：EcoPaste（Tauri v2 剪贴板管理器，v1.1.0）已在 src-tauri/src/window/macos.rs 落地了与 Maccy 同构的方案：
rust
tauri_panel! {
    panel!(MainPanel {
        config: {
            is_floating_panel: true,
            can_become_key_window: true,      // 能成为 key window，接收键盘
            can_become_main_window: false
        }
    })
}
panel.set_style_mask(StyleMask::empty().resizable().nonactivating_panel().into());
panel.set_collection_behavior(
    CollectionBehavior::new().stationary().move_to_active_space().full_screen_auxiliary().into()
);
panel.show_and_make_key();   // ← 等价 Maccy 的 makeKey()：拿键盘焦点但不激活 App
  • 它甚至已踩过并解决了最隐蔽的坑，注释写得很明确：面板处于 key window 时，合成出来的 CGEvent ⌘V 会被面板自己吞掉。解法是粘贴前 resign_key_window()，粘贴后 make_key_window() 把焦点拿回来（macos.rs:180-204）。

所以 Phase 0 的性质从「可行性验证」变为「接入适配 + 关键坑复现」：不是问「能不能做」，而是问「在 QuickQuick 现有 popover.rs 的焦点编排（NSApplication.activate() + set_focus）之上，如何替换成 panel 语义，并保留已有的辅助功能降级路径」。

参考实现的价值不止于此——EcoPaste 还解决了全屏 Space 下的显示策略（move_to_active_space 与 can_join_all_spaces 的切换时机）、失焦自动隐藏（window_did_resign_key）、to_panel 的逆操作与生命周期还原（lifecycle/mod.rs:650）。这些都是 QuickQuick 会遇到的同类问题。

判断四：QuickQuick 当前最大的问题不是缺功能，是「承诺与实现脱节」。 审计发现一批代码写了但运行期不可达的能力：

能力实现状态实际效果
跳过敏感内容（concealed/transient）privacy.rs:97-117 逻辑完整is_concealed 硬编码 false，永不生效
按来源应用排除名单管理链齐全source_app 硬编码 None，永不生效
防自污染（私有 UTI）trait 文档承诺has_self_marker 恒 false，未实现
翻译缓存（四元组 + LRU）cache.rs 196 行 + 建表零生产调用，每次翻译都走网络
翻译重试 / 取消 / 错误归一retry.rs/cancel.rs/error.rs全部零生产调用
可移植备份（口令加密包）portable.rs 格式加密完整只被测试调用，无 IPC、无 UI

这类问题的严重性高于「功能缺失」：设置页在向用户撒谎。用户配了排除名单、开了敏感跳过，实际密码管理器内容照样入库。

判断五：翻译、加密、跨平台、富文本是 Maccy 结构上不可能有的资产，重构不能伤到它们。 QuickQuick 有 21 个翻译源、SQLCipher 整库加密 + 机器绑定密钥、Windows 双端、HTML 全链路保真、内置签名自动更新、离线 ECDICT 词典。这是差异化护城河。任何交互重构都必须先确认不破坏这些链路。

1. 调研方法与证据边界

1.1 用了什么

手段对象产出
REA inspect_macho / inspect_plist / inspect_signature / inspect_artifactMaccy 2.6.1 发布态依赖（仅 Sparkle 2.6.4）、31 语言、LSUIElement、沙盒与 XPC 更新架构

只读代码审计QuickQuick 全域能力矩阵、死代码清单、性能链条

1.2 反编译器：已装但未接入，且判定为非关键路径

本轮已安装 OpenJDK 21 + Ghidra 12.1.4（~/tools/ghidra_12.1.4_PUBLIC），REA doctor 对 install/version/headless/java 四项均报 healthy，但卡在最后一步：Ghidra 官方发布包只含 linux_x86_64 与 win_x86_64 的 native decompiler，macOS arm64 需本地编译，而 Makefile 硬编码 x86_64、depend 规则不透传 BFD include，两次编译均失败。

判定放弃的理由（不是「懒得装」）：

  1. Maccy 是 MIT 开源，源码可读，比伪代码更快更准；
  2. 发布版与源码的一致性已由 sha256 绑定 + 类名/字符串逐条交叉印证（2.6.1 / build 60 与 appcast pubDate 一致）；
  3. REA 的 Ghidra provider 对 universal Mach-O 报 architecture_unsupported，还需先 thin slice，多一层麻烦；
  4. Maccy 二进制已 strip（exports 仅 1 个），Swift 类型名在元数据 section，反编译产出是 FUN_xxx + 指针运算，边际价值低。

保留状态：Ghidra 已就位，未来若需要验证闭源目标（无源码可读时），只差编译 native decompiler 这一步。

1.3 拿不到的（明确记录）

  • Maccy 的实际 SQLite 物理 schema（本机容器为空，从未使用过该 app；物理 schema 由 SwiftData 运行时生成）
  • SwiftUI 视图树的精确层级与 modifier 顺序（SwiftUI 无 nib，IB 解析不到 Maccy 自身文档）
  • Glass / VisualEffect 的最终视觉参数（系统渲染决定）
  • 运行时观察 = 0 项：Maccy 的 FloatingPanel 在 resignKey() 里无条件 close()，窗口存活约 2s，跨不过一次 MCP 调用；REA 只接受 onscreen 窗口，而该 panel 的 kCGWindowIsOnscreen 为空

影响评估：不影响能力矩阵与设计决策；轻度影响像素级 UI 复刻（需真机开一次 Maccy 校准行高/留白/字体）。

3. 需要你裁决的五个取舍

方案的形状取决于这五个问题的答案。我给出推荐，但这是你的产品判断。

Q1｜交互架构路线：已定，走非激活面板（附适配 spike）

结论：走 Maccy/EcoPaste 路线，不再考虑「激活 + 前台应用恢复」的降级方案。

理由见判断三：tauri-nspanel + EcoPaste 已证明 Tauri v2 webview 能在非激活面板里拿到键盘焦点，且关键坑（粘贴时面板吞掉 CGEvent ⌘V）已有明确解法。

仍保留一个短 spike（约 1 天），但性质是「适配验证」而非「可行性验证」，只确认三件事：

  1. QuickQuick 现有 popover.rs:122-152 的 NSApplication.activate() + set_focus() 编排，替换为 show_and_make_key() 后，原前台应用是否仍保持 active
  2. webview 内 <input autofocus> 能收到字符（中文输入法 composition 事件是否正常）
  3. 「resign_key_window → 注入 ⌘V → make_key_window」这套编排，与 QuickQuick 现有「hide 窗口 + hide app + 等 350ms + 注入」（ipc/system.rs:69-78）如何合并——注意现有代码是「隐藏整个 app」，panel 语义下应改为「仅 resign key」，这是最容易改错的一处

为什么不能跳过这个 spike：不是怀疑可行性，而是 QuickQuick 现在的粘贴编排是围绕「隐藏 app」设计的。panel 化之后这个假设失效，改错会导致「粘贴到错误应用」或「面板消失后无法继续操作」。

Q2｜「全面看齐」的范围：一次到底，还是分两版？

推荐：分两版。v0.4 还债 + 交互地基；v0.5 捕获/规则/存储/产品化。

理由：L0 诚信债 + L1 交互是用户当前体感最痛的两块，且它们互相独立于 L2/L3。L2 的「任意 UTI 遍历」需要换掉 arboard、直连 NSPasteboard，是架构级改动，风险独立，不该和交互重构挤在同一版。

Q3｜i18n：做 31 语言，还是先中英双语？

推荐：v0.5 只做「i18n 框架 + 中英双语」，语言数后续按需求扩。

Maccy 的 31 语言靠 BartyCrouch + DeepL 机翻管线自动铺开，但它的出货闸门是 knownRegions 白名单——机翻铺满 41 个目录，只有被信任的 31 个进包。这个工程思路值得抄（框架 + 白名单），但一次性上 31 语言对当前阶段是负担，且 QuickQuick 的文案量（6 区设置 + 3 个窗口）远大于 Maccy 的窄界面。

Q4｜死代码：接线还是删除？

推荐：逐个判定，不搞一刀切。

模块建议理由
隐私三件套（concealed/source_app/self_marker）接线用户已能看到配置项，且这是隐私承诺
portable.rs 备份接线解决「换机即失去全部历史」的真实痛点，格式已完整
tiered_cleanup接线存储页已承诺此行为
翻译 cache.rs接线直接减少网络请求与免费源限流
翻译 retry.rs / cancel.rs / error.rs接线免费源失败率高的根因
AppStoreReview 类死代码（Maccy 侧）不适用—

Q5｜翻译域是否同期修？

推荐：v0.4 顺带接线（缓存/重试/取消），不新增翻译功能。

理由：翻译是差异化资产，但当前「21 个源下面没有缓存/重试/取消」的状态会持续损耗它的价值。接线是低成本高回报，而新增源/流式输出/划词即译应等剪贴板域稳定后再说。

4. 分阶段方案

Phase 0｜接入适配 spike（约 1 天）

性质：不是可行性验证（已有先例），是接入方式验证。

任务产出通过标准
引入 tauri-nspanel，把 clip-popover 窗口 to_panel 成 NSPanel，置 can_become_key_window: true + nonactivating_panel styleMask可运行 PoC面板打开时 NSWorkspace.frontmostApplication 不变

5. 不做的事（明确边界）

项理由
粘贴栈 / 多选队列Maccy 没有；它用字母 pin + 数字直达覆盖了 80% 场景。若要做，是超越项，应单独立项，不在「看齐」范围内
右键菜单Maccy 没有（全量 grep 0 命中）。QuickQuick 现有 ⌥⌫/⌥P 键位已能覆盖，右键菜单收益低于成本
AppIntents / ShortcutsTauri 无法生成 Metadata.appintents，这是硬边界
沙盒Maccy 因沙盒才需要 Downloader.xpc/Installer.xpc 那套复杂架构。QuickQuick 不上沙盒，tauri-plugin-updater 直接够用，不要复刻
Core Data / SwiftData无意义，继续用 rusqlite
像素级 1:1 复刻 Maccy 视觉行高 22pt、padding 5/10 等常量可参考，但 QuickQuick 有自己的 OKLch token 体系，应保持视觉自主
Ghidra native decompiler 编译见 §1.2，非关键路径；已保留 Ghidra 待未来验证闭源目标

8. 一页纸结论

Maccy 不是「功能更多的剪贴板管理器」，而是「把窄路径打磨到极致的交互范本」。它的杀手锏只有三个：非激活面板（消灭前台应用恢复类 bug）、cycle 模式（把选+粘压成一次肌肉动作）、预计算 title + 内存过滤（200 条列表秒开）。它的空缺（无引导、无 AND 搜索、无导入导出、音效搭通知权限）可以直接超越。

QuickQuick 要「全面看齐」，真正的工程量集中在十个原生桥接模块。交互架构那条路已经通了——tauri-nspanel + EcoPaste 证明了 Tauri v2 webview 能在非激活面板里拿到键盘焦点，连「面板吞掉合成 ⌘V」这个最隐蔽的坑都有现成解法。剩下的是适配与工作量，不是赌运气。

在此之前，有一批更该先还的债：设置页正在向用户承诺它并未实现的能力。这件事的优先级高于任何新功能。
